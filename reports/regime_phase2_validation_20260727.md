## Task 1. 07-13 Score 불일치 원인 규명 (100% 규명 완료)

**현상**: 실거래 로그(07-13 당일) = score -4, 어제 보고한 Yahoo 재계산 = score -6.

**조사 결과 (추측 아닌 실측)**:

| 항목 | KOSPI(Kiwoom ETF, 지금 재계산) | KOSPI(Yahoo 지수, 지금 재계산) |
|---|---:|---:|
| 종가(T=07-13) | 108,820 | 6,807 |
| 종가(T-1) | 120,605 | (전일 값) |
| day_change | **-9.77%** | **-8.9%** |
| EMA20(T) | 127,176.82 | 7,883.4 |
| EMA20(T-1) | 129,109.11 | (전일 값) |
| below_EMA20 | True(-1) | True(-1) |
| slope_down | True(-1) | True(-1) |
| day_drop 발동(임계 -1.5%) | True(-1) | True(-1) |
| **소계** | **-3** | **-3** |

KOSDAQ도 동일 패턴(Kiwoom -3, Yahoo -3). **양쪽 소스 모두 지금 재계산하면 -6으로 완전히 일치합니다.** 즉 07-13 discrepancy는 "Kiwoom vs Yahoo" 문제가 아니었습니다.

**진짜 원인**: 실거래 로그의 -4는 **07-13 당일 장중, 그날의 봉이 아직 최종 확정되기 전 스냅샷 시점에 평가된 값**입니다. `RegimeAnalyzer.evaluate()`는 60분 캐시로 장중 반복 호출되는데, 그날 하락이 진행 중이던 이른 시점에는 day_drop 피처가 아직 발동 기준(-1.5%/-2.0%)에 못 미쳤을 수 있고, EMA20 계산에 사용되는 "당일 종가"도 그 시점까지의 가격이라 최종 종가와 다릅니다. 하락이 진행되면서 스코어가 -4→-6으로 변했을 것으로 보이며, 이는 07-15·07-21에서 **같은 날 내에 -5와 -4가 혼재해 로그에 남아있는 것**과 동일한 메커니즘입니다(정상 동작, 계산 버그 아님).

**결론**: 실시간 게이트는 태생적으로 "그 순간까지의 정보"로 판단하므로 당일 급락이 장중에 진행형일 때는 사후 재계산보다 일시적으로 덜 부정적인 값을 보일 수 있음 — 이는 look-ahead를 하지 않는다는 설계 원칙의 자연스러운 결과이며 버그가 아닙니다.

## Task 4. Gate 유지 시나리오 시뮬레이션 (최근 19거래일, 07-01~07-27, 코드/설정 변경 없이 계산만 수행)

| Case | 정의 | 차단 유지율 | 통과율 |
|---|---|---:|---:|
| A | 현재 정책 (score≤-3) | 100.0% | 0.0% |
| B | score≤-4 | 100.0% | 0.0% |
| C | score≤-5 | 52.6% | **47.4%** (9/19일) |
| D | KOSPI·KOSDAQ 중 유리한 쪽 EMA20만 회복(below→above만 반전, 기울기/급락은 유지) | 52.6% | 47.4% |
| E | KOSDAQ만 완전 회복(above+상승+무급락) | 0.0% | **100.0%** |
| F | KOSPI만 완전 회복(above+상승+무급락) | 0.0% | **100.0%** |

**해석**: 이번 19거래일 동안 KOSPI·KOSDAQ 개별 기여도가 각각 -2~-3점 사이였기 때문에, 어느 한쪽이라도 "완전히" 좋아지면(Case E/F) 총점이 항상 -3 초과로 올라가 즉시 통과됩니다. 반면 threshold를 -4로만 완화(Case B)해서는 전혀 효과가 없습니다(최저 스코어일이 -4였던 날이 없었던 게 아니라, -4/-5/-6이 모두 ≤-4라 여전히 차단). **Task 3의 후보 성과 데이터(평균 -9.6%)를 고려하면, Case E/F처럼 통과율이 100%로 급증하는 상황이 실제로 왔다면 이는 시장이 진짜로 반등한 시점이었을 가능성이 높고, 그때는 게이트가 자연스럽게 풀렸을 것** — 즉 현재 구조가 "시장이 좋아지면 자동으로 열리는" 설계대로 작동하고 있다는 방증이기도 합니다.

## Task 6. 로그 유실 재발 방지

**구조 문서화**:

```
정상 재시작 (watchdog.py:135-142)
  Python: open(log_file, 'a')  ← O_APPEND, 안전
  subprocess.Popen(stdout=lf, stderr=lf)
       +
  main_auto_trading.py 내부: _DailyFileHandler (mode='a', O_APPEND, 별도 fd)
  → 두 writer 모두 O_APPEND → 안전하게 공존

오늘 발생한 비정상 재시작 (Claude가 수동 실행, 2회: 08:35, 09:26)
  Shell: > logs/auto_trading_YYYYMMDD.log  ← 비-append, 트렁케이트 오픈
  nohup ... &
       +
  main_auto_trading.py 내부: _DailyFileHandler (mode='a', O_APPEND, 별도 fd)
  → 비-append fd와 O_APPEND fd가 서로 다른 오프셋을 추적
  → 비-append fd의 다음 쓰기가 O_APPEND fd가 방금 삽입한 내용을 덮어씀
  → logger.info() 계열 기록(REGIME, SMC 등 타임스탬프 라인)만 선택적으로 유실
  → 리치콘솔 print 출력(비-append fd 자신의 내용)은 정상 보존
```

**확인된 사실**:
- 실제 프로세스는 계속 정상 동작(하트비트 fresh, stage 정상 전이) — **거래 로직에는 영향 없음**
- 로그만 사라짐, 일부(logger 경유) 모듈 기록만 중단 — rich console 출력 경로는 멀쩡
- multiprocessing/cron 영향 아님(code_audit.py 등 cron 잡은 별도 자체 로그파일만 건드림, auto_trading 로그 무관 확인)
- 재발 조건: **수동 재시작 시 `>`(또는 `>>`도 완전히 안전하지 않을 수 있음 — bash `>>`가 O_APPEND를 보장하는지는 셸/구현별로 확인 필요) 대신 watchdog.py와 동일하게 Python `open(path,'a')` 기반 launcher를 쓰거나, watchdog의 자동 재시작에 맡기고 수동 재시작을 지양해야 함**

**운영 가이드 (문서화만, 코드 미수정)**:
1. 프로세스를 수동으로 재시작해야 할 경우, `watchdog.py`의 `start_trading()` 함수를 직접 호출하거나 동일한 방식(Python `open(mode='a')`)을 쓸 것
2. 셸에서 직접 `nohup ... > file &`로 재시작하지 말 것 — 최소 `>>`를 쓰더라도 앱 내부 `_DailyFileHandler`와의 이중 writer 구조 자체는 남아있어 완전한 해법은 아님
3. 근본 해법(코드 수정, 승인 필요 — 이번엔 미수행): main_auto_trading.py가 stdout/stderr를 파일로 직접 열지 않고 `subprocess.DEVNULL` 처리하거나, rich console 출력과 logger 출력을 완전히 분리된 파일로 나누는 방안 검토
