## 3. 확인된 결함 2건

### 결함 A — peak 오염 (과거 · 수정 완료)

```
2026-06-10 08:45:07  [EQUITY_CTRL] peak 복원: 5,201,030원
2026-06-10 14:55:00  [EQUITY_CTRL] 신고점 갱신: 5,201,030 → 10,000,000원
```

`main:2776 self.total_assets = 10000000` 은 **계좌조회 실패 시 폴백값**이다.
이 값으로 `update_peak()` 가 호출돼 peak 이 실제 계좌의 약 2배로 굳었다.
결과: 06-18 ~ 07-10 의 dd 가 최대 -83.9% 로 부풀려졌다.

**수정됨** — 2026-07-12 `_account_data_reliable` 가드가 main:2830 / main:12085
두 갱신 경로 앞에 추가됐고 peak 이 4,467,501 로 복구됐다.
2026-07-23 이후 매 기동 로그가 `peak 복원(primary): 4,467,501원` 로 일정하다.

자세한 내용: `PEAK_TIMELINE.md`

### 결함 B — 매도 미결제 대금 누락 (미수정)

`total_assets = pymn_alow_amt(출금가능금) + positions_value` 이므로
매도 직후에는 포지션도 없고 매도대금도 아직 출금가능금이 아니다.

```
05-21 EOD equity   4,988,840
05-22 SELL          4,526,860        (trades)
05-22 잔고 로그     542,250원 (총자산: 542,250원)
05-22 EC_HALT dd    -90.0%
06-19 EC_HALT equity 4,773,205       ← 돈은 그대로 있었다
```

**계좌가 89% 증발한 것이 아니라 계산에서 빠진 것이다.**
이 상태에서 EC_HALT 가 dd -90% 로 차단했다.

자세한 내용: `DRAWDOWN_VALIDATION.md`

## 4. Threshold 민감도 — 임계값은 원인이 아니다

EC_HALT 로그의 equity 실측치로 **EOD 기준 peak 을 재구성**해
(정책과 동일하게 `eod_only_peak=True` 를 적용) 임계값별 차단 일수를 계산했다.

| Threshold | 차단 | 해제 |
|---|---|---|
| -18% | 17/29일 | 12일 |
| -20% | 17/29일 | 12일 |
| -22% | 17/29일 | 12일 |
| -25% | 17/29일 | 12일 |
| -30% | 17/29일 | 12일 |

**-18% 를 -30% 로 완화해도 차단 일수가 한 날도 줄지 않는다.**
dd 분포가 양극(-2~-16% 또는 -31% 이하)이라 그 사이에 걸친 날이 없기 때문이다.

→ **임계값 조정은 무의미하다. 문제는 equity 입력값과 peak 이었다.**

⚠️ 한계: 이 재구성은 EC_HALT 가 실제로 기록된 29일의 equity 만 쓴다.
신호가 없어 EC_HALT 가 안 찍힌 날의 equity 는 관측되지 않았으므로
재구성 peak 은 **하한**이고 dd 는 **상한**(덜 부정적)이다.
"12일은 차단되지 않았을 것" 은 이 표본 안에서의 결과다.
